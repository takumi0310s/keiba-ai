# V15 死因解剖（v15_autopsy）

**問い**: 「6/27以降 JRDB全滅→V15スコア崩壊」が運用悪化（停止）の主因か？
**検証**: cumulative_results 週別ROI / T1_features_audit / v15_feat_dump ライブ特徴（読み取りのみ）。

---

## 結論（3行）
1. ★**ROI低下は JRDB死より前・5月から進行**（4月109% → 5月78.6% → 6月前半67.8%）＝**主因は「JRDB死」単独ではない**（エッジ減衰/市場適応が先行）。
2. ★**JRDB は ~6/22-26 に全滅**（feat_dump: 6/21まで生・6/27で40/40定数）→ V15本番スコアも圧縮（8/2は0.14-0.32 vs 健全日0.0-0.9）＝**二次的なデータ品質崩壊**。
3. ★**監視が完全にゾンビ**（T1_features_audit は全日 byte-identical・学習キャッシュを監査しライブを見ていない）→ **JRDB死を構造的に検知不能→アラート不発**。判定=**「両方」＋監視失敗**。

## 2. JRDB データ死（二次要因）
- v15_feat_dump のライブ JRDB特徴 定数化: 6/13=2/40, 6/20=3/40, 6/21=6/40（生）→ **6/27=40/40（全滅）**。死亡窓 **6/22-6/26**。
- 影響: Pattern A 予測が corr(本番)0.99→0.01・範囲圧縮。**V15本番スコアも 0.14-0.32 に圧縮**（識別能力喪失）。
- 背景: JRDB は元々不安定（CLAUDE.md: jrdb_sed 5/9停止→6/7復旧→~6/24再死）。**5月の低下にもデータ不安定が寄与した可能性**。

## 3. ★監視失敗＝真の運用バグ★
- **T1_features_audit_2026_*.json は 5/17-8/9 の全日 byte-identical**（md5一致）。
- 監査対象 = **学習キャッシュ(2020-25 静的)**。証拠: audit の `jrdb_idm` unique=711/mean=37.66（=キャッシュ値）に対し、**ライブ8/2は unique=1/mean=50（死）**。
- → 監視は毎日「JRDB死=1/40（健全）」を出し続け、**ライブの40/40死を一度も検知しなかった**。アラートが不発だった構造的理由。
- **台帳欠落**: 6/22-7/26 は cumulative_results に0行だが、race_notify_log_v2 は 6/27・6/28・7/11 稼働＝**予測は動作・記録(daily_results→台帳)が停止**した別の記録失敗。

## 4. 判定: 「両方」＋監視失敗
- **一次**: エッジ減衰/市場適応（ROI低下は5月から・JRDB健全期でも67.8%）。
- **二次**: JRDB全滅(~6/24)によるデータ品質崩壊（特徴40/40死・本番スコア圧縮）。
- **増幅**: 監視ゾンビ化で①も②も検知されず、③台帳欠落で成績可視性も喪失 → 運用が「見えないまま悪化」。
- ★「6/27 JRDB死が主因」仮説は**部分棄却**（低下は先行）。ただしJRDB死は無視できない二次要因。★

## 5. 推奨（運用不変原則の範囲で提言のみ）
1. **T1監視のライブ化**: 監査対象を学習キャッシュ→当日 feat_dump に変更（ゾンビ検知＝内容ハッシュ日次変化チェック）。
2. **JRDB死のライブ番兵**: 予測直前に JRDB特徴の unique/定数率を検査、閾値超で予測ブロック or degraded明示。
3. **台帳記録の監視**: cumulative_results の日次追記が途切れたら警告（6/22-7/26の再発防止）。
4. **エッジ減衰対応**: 5月からの低下は再学習(v16f等)やレース選択の見直しが本筋。データ修復だけでは109%には戻らない見込み。

*注: 本レポートは診断のみ。V15 pkl・運用系コードは不変。修正は別途承認後。*
